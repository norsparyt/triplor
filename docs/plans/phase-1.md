# Phase 1 implementation plan: core backend

Parent document: [../ARCHITECTURE.md](../ARCHITECTURE.md). Next: [phase-2.md](phase-2.md).

**Status (2026-11-11):** not started. Nothing here has been compiled or run yet; the SQL and Dockerfiles are untested drafts. Versions were checked on 2026-11-10 against Spring Initializr, Maven Central and Docker Hub.

## Outcome

Three Spring Boot services (identity, adventure, chat) run under Docker Compose with PostgreSQL and MongoDB, are covered by unit and Testcontainers tests, and have a recorded load-test baseline.

A scripted flow passes end to end: two users register and are verified, one creates a trip, the other finds it by search and asks to join, the organizer accepts, and both see the conversation.

Out of scope until Phase 2: Kafka, Redis, the gateway, WebSockets and notifications. The accept step calls chat synchronously on purpose, so Phase 2 has a measured "before".

| Decision | Choice | Reason |

## M1: Shared library and identity (accounts and tokens)

**Goal:** register, log in, refresh and log out, with tokens other services can verify without calling identity.

**Status:** built and passing (62 tests across `common` and `identity`), and smoke-tested over HTTP against the Compose database.

Differences from the original plan:

- The `profiles` table is created in this milestone (`V2__profiles.sql`), because registration stores the display name. The verification table moves to `V3` in M2.
- Token verification in adventure and chat uses Spring Boot's own `spring.security.oauth2.resourceserver.jwt.*` properties; the shared library adds only the filter chain, role mapping and error rendering.
- The MongoDB container definition is added in M6, when chat first needs it.
- The Compose database is published on host port 5433, because a native PostgreSQL on 5432 would otherwise answer on `localhost`.
- The signing-key path is bound as a string. A relative path cannot be bound to `java.nio.file.Path` inside a web application.

### `libs/common`

Keep it thin: cross-cutting code only, never domain types.

- [x] Error handling: `ApiException(code, status, detail)` and a `@RestControllerAdvice` that turns it, bean-validation failures and malformed requests into problem JSON (`type`, `title`, `status`, `detail`, `code`, `errors[]`).
- [x] Resource-server security configuration: JWKS URI, issuer and audience validation, a converter from the `roles` claim to authorities, stateless sessions, CSRF off.
- [x] `CurrentUser` (id, roles, verified) resolved from the JWT as a controller argument.
- [x] A `Clock` bean. Inject time everywhere; tests use a fixed clock.

### `libs/test-support`

- [x] A test RSA key, a decoder configured with its public half, and a factory that mints tokens for any user, role and verified flag. Other services use it so their tests never need identity running.
- [x] Shared Testcontainers definitions (Postgres from the custom image, declared as a compatible substitute for `postgres`; MongoDB).

### Identity schema (Flyway `V1__accounts.sql`)

```sql
CREATE TABLE users (
  id            uuid PRIMARY KEY,
  email         text NOT NULL UNIQUE CHECK (email = lower(email)),
  password_hash text NOT NULL,
  role          text NOT NULL DEFAULT 'USER'   CHECK (role IN ('USER', 'ADMIN')),
  status        text NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'SUSPENDED')),
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE refresh_tokens (
  id          uuid PRIMARY KEY,
  user_id     uuid  NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  family_id   uuid  NOT NULL,
  token_hash  bytea NOT NULL UNIQUE,          -- SHA-256 of the opaque token
  expires_at  timestamptz NOT NULL,
  revoked_at  timestamptz,
  replaced_by uuid,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX refresh_tokens_family_idx ON refresh_tokens (family_id);
CREATE INDEX refresh_tokens_user_idx   ON refresh_tokens (user_id);
```

Emails are lower-cased by the application before every read and write; the check constraint catches any code path that forgets.

### Token design

- **Access token:** claims `sub` (user id), `roles`, `verified`, `iss`, `aud`, `iat`, `exp`, `jti`. Signed with RS256 using `NimbusJwtEncoder`. The key ID is the public key's thumbprint, so the JWKS endpoint can later publish two keys during rotation.
- **Signing key:** `make keys` generates a development key into the git-ignored `.local/` folder with `openssl genpkey`. Identity reads the path from an environment variable. No key is ever committed, including development keys.
- **Refresh token:** 256 random bits, returned once, stored only as a SHA-256 hash.
- **Passwords:** BCrypt through Spring Security's `PasswordEncoder`. Login runs the hash check even when the email is unknown, so timing does not reveal which emails exist.

Refresh rotation, in one transaction:

1. Hash the presented token and select its row `FOR UPDATE`.
2. Not found or expired: 401.
3. Already revoked: this is reuse. Revoke every live token in the same `family_id`, then 401.
4. Otherwise mark it revoked, set `replaced_by`, insert a new token in the same family, and issue a new access token.

Two refreshes fired at once with the same token look like reuse and log the user out. The Flutter client must therefore run only one refresh at a time (Phase 3). Add a short server-side grace window only if that proves insufficient.

### Endpoints

| Method and path | Auth | Success | Errors |
|---|---|---|---|
| `POST /auth/register` | none | 201 with user and both tokens | 400 `VALIDATION_FAILED`, 409 `EMAIL_TAKEN` |
| `POST /auth/login` | none | 200 with both tokens | 401 `INVALID_CREDENTIALS`, 403 `ACCOUNT_SUSPENDED` |
| `POST /auth/refresh` | none | 200 with a new pair | 401 `INVALID_REFRESH_TOKEN` |
| `POST /auth/logout` | none | 204, also when the token is unknown | |
| `GET /.well-known/jwks.json` | none | 200 with the public key set | |

Request bodies: register takes `email`, `password` (10 characters minimum) and `displayName`; login takes `email` and `password`; refresh and logout take `refreshToken`.

### Tests

- [x] Unit: token claims and expiry with a fixed clock; each branch of refresh rotation.
- [x] Web slice: validation failures produce problem JSON with field errors.
- [x] Integration (Testcontainers Postgres): register then log in; duplicate email returns 409; a rotated refresh token works once; reusing the old one revokes the family, so the new one fails too; every issued token's key ID appears in the JWKS document.

**Done when:** the integration tests pass and a token from identity is accepted by a throwaway protected endpoint using only the JWKS URL.

**Be able to explain:** RS256 with JWKS versus a shared HS256 secret; why refresh tokens are opaque, hashed and rotated; what reuse detection protects against; why the access token is short-lived.

CREATE TABLE profiles (

## M3: Adventure (schema, places, CRUD with idempotency)

**Goal:** create, read, edit and cancel adventures safely under retries and concurrent edits.

### Schema

```sql
-- V1__extensions.sql  (no-ops when the init script already created them)
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- V2__places.sql
CREATE TABLE places (
  id           bigint PRIMARY KEY,               -- GeoNames id
  name         text NOT NULL,
  ascii_name   text NOT NULL,
  admin1       text,
  country_code text NOT NULL CHECK (char_length(country_code) = 2),
  lat          double precision NOT NULL,
  lng          double precision NOT NULL,
  population   bigint NOT NULL DEFAULT 0
);
CREATE INDEX places_name_trgm_idx ON places USING gin (lower(ascii_name) gin_trgm_ops);

-- V3__adventures.sql
CREATE TABLE adventures (
  id           uuid PRIMARY KEY,
  organizer_id uuid NOT NULL,
  place_id     bigint NOT NULL REFERENCES places (id),
  lat          double precision NOT NULL,
  lng          double precision NOT NULL,
  location     geography(Point, 4326)
               GENERATED ALWAYS AS (ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography) STORED,
  start_date   date NOT NULL,
  end_date     date NOT NULL,
  trip_dates   daterange GENERATED ALWAYS AS (daterange(start_date, end_date, '[]')) STORED,
  styles       text[] NOT NULL,
  description  text NOT NULL CHECK (char_length(description) BETWEEN 1 AND 300),
  capacity     int  NOT NULL CHECK (capacity BETWEEN 1 AND 20),
  seats_taken  int  NOT NULL DEFAULT 0,
  status       text NOT NULL DEFAULT 'OPEN'
               CHECK (status IN ('OPEN', 'FULL', 'CANCELLED', 'COMPLETED')),
  version      bigint NOT NULL DEFAULT 0,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT adventures_dates_chk  CHECK (end_date >= start_date),
  CONSTRAINT adventures_seats_chk  CHECK (seats_taken BETWEEN 0 AND capacity),
  CONSTRAINT adventures_styles_chk CHECK (
    cardinality(styles) BETWEEN 1 AND 6
    AND styles <@ ARRAY['ADVENTURE','BACKPACKING','RELAXING','FOODIE','CULTURE','HIKING']::text[])
);
CREATE INDEX adventures_location_gix  ON adventures USING gist (location);
CREATE INDEX adventures_dates_gix     ON adventures USING gist (trip_dates);
CREATE INDEX adventures_styles_gin    ON adventures USING gin (styles);
CREATE INDEX adventures_organizer_idx ON adventures (organizer_id, start_date DESC);
CREATE INDEX adventures_open_feed_idx ON adventures (start_date, id) WHERE status = 'OPEN';

-- V4__idempotency_keys.sql
CREATE TABLE idempotency_keys (
  user_id         uuid  NOT NULL,
  idem_key        text  NOT NULL CHECK (char_length(idem_key) BETWEEN 8 AND 128),
  operation       text  NOT NULL,
  request_hash    bytea NOT NULL,
  response_status int,
  response_body   jsonb,
  created_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, idem_key)
);
CREATE INDEX idempotency_keys_created_idx ON idempotency_keys (created_at);
```

`capacity` counts travellers who can join, not including the organizer. `adventures_seats_chk` is the backstop: even if application logic is wrong, the database refuses to oversell.

### Entity mapping rules

- [ ] `location` and `trip_dates` are generated by the database from plain columns and are not mapped in the entity. The ORM sees only numbers and dates; PostGIS and the range index are used from native queries.
- [ ] The `Adventure` entity is used for inserts and reads only; mark it `@Immutable`. After the insert, every change to the row is one explicit SQL statement: edit, cancel, take a seat. An ordinary entity save could otherwise write back a stale seat count.
- [ ] `seats_taken` and `status` are never set from Java, not even on insert; the column defaults apply.
- [ ] `styles` maps to `String[]` with the array JDBC type.
- [ ] `version` is incremented by every edit statement and doubles as the ETag.
- [ ] A base entity implementing `Persistable<UUID>`, so `save()` on a new object inserts without a prior select.
- [ ] `spring.jpa.hibernate.ddl-auto=validate` and `spring.jpa.open-in-view=false`. Flyway owns the schema.
- [ ] Identity uses JPA the ordinary way, with managed entities and dirty checking. The restrictions above exist because `adventures` carries a counter that must never be overwritten.

### Places

- [ ] `infra/scripts/seed-places.sh`: download the GeoNames `cities1000` dump, load it into a staging table with `\copy`, and insert the needed columns into `places`. Keep the data file out of git and credit GeoNames (CC BY 4.0) in the README.
- [ ] `GET /places?q=&limit=`: at least two characters; match `lower(ascii_name) LIKE :q || '%'`, order by population, default limit 8.
- [ ] Integration tests use a fixture of about twenty places.

### Idempotency

The key is required on the two creates, where a retry would otherwise produce a duplicate. Accept, reject and withdraw need no key because the state machine already makes them idempotent. The client may send the header on every write; the server only requires it here.

Inside the same transaction as the business write:

1. `INSERT INTO idempotency_keys (user_id, idem_key, operation, request_hash) VALUES (...) ON CONFLICT (user_id, idem_key) DO NOTHING`.
2. One row inserted: this is the first attempt. Run the business logic, then store the response status and body on the key row. Commit.
3. No row inserted: the key exists. If its `request_hash` differs, return 422 `IDEMPOTENCY_KEY_REUSED`. Otherwise return the stored response with the header `Idempotent-Replayed: true`.

Two requests with the same key in flight at once need no extra locking. The second `INSERT` waits on the unique index until the first transaction finishes, then either sees the stored response or, if the first rolled back, becomes the first attempt itself.

Failed operations roll back and store nothing, so a retry is evaluated afresh. `request_hash` is SHA-256 over the operation name and the validated request serialized with sorted keys.

### Endpoints

| Method and path | Rules |
|---|---|
| `POST /adventures` | Verified users. `Idempotency-Key` required. Body: `placeId`, `startDate`, `endDate`, `styles`, `description`, `capacity`. Returns 201 with `Location` and `ETag` |
| `GET /adventures/{id}` | Returns the adventure, `interestedCount` (pending requests) and `viewerRequest` (the caller's own request, if any), with an `ETag` |
| `PATCH /adventures/{id}` | Organizer only. `If-Match` required (428 without it, 412 on mismatch). Capacity cannot drop below `seats_taken` |
| `DELETE /adventures/{id}` | Organizer only. Sets `CANCELLED` and rejects pending requests in the same transaction. 204, also when already cancelled |
| `GET /adventures/mine?role=` | Adventures the caller organizes or has joined |

An edit is a single conditional statement. This is optimistic locking written out by hand:

```sql
UPDATE adventures
   SET start_date  = COALESCE(CAST(:startDate AS date), start_date),
       end_date    = COALESCE(CAST(:endDate AS date), end_date),
       styles      = COALESCE(CAST(:styles AS text[]), styles),
       description = COALESCE(CAST(:description AS text), description),
       capacity    = COALESCE(CAST(:capacity AS int), capacity),
       status      = CASE WHEN seats_taken >= COALESCE(CAST(:capacity AS int), capacity)
                          THEN 'FULL' ELSE 'OPEN' END,
       version     = version + 1,
       updated_at  = now()
 WHERE id = :id
   AND version = :expectedVersion
   AND status IN ('OPEN', 'FULL')
   AND seats_taken <= COALESCE(CAST(:capacity AS int), capacity);
-- 0 rows: re-read to answer 412 VERSION_CONFLICT, 409 ADVENTURE_NOT_OPEN or 409 CAPACITY_BELOW_SEATS.
```

A changed `placeId` also sets `place_id`, `lat` and `lng` in the same statement, after looking the place up. Check ownership (403) with a plain read before running it.

### Tests

- [ ] Unit: date and capacity rules; the request-hash canonicalisation.
- [ ] Web slice: missing `Idempotency-Key` returns 400; missing `If-Match` returns 428; an unverified caller gets 403 `NOT_VERIFIED`.
- [ ] Integration: the same key replayed returns the identical body and leaves one row; the same key with a different body returns 422; two threads posting the same key at once leave one row; a stale `If-Match` returns 412; cancelling rejects pending requests.

**Done when:** all of the above pass against the custom Postgres image.

## M4: Adventure (discovery search and matches)

**Goal:** find open trips by place, dates and style, fast, with stable pagination.

### Search

`GET /adventures/search?lat&lng&radiusKm&from&to&styles&cursor&limit`. Defaults: radius 50 km (maximum 500), dates from today to 90 days ahead, limit 20 (maximum 50).

```sql
SELECT a.id, a.organizer_id, a.place_id, a.start_date, a.end_date, a.styles,
       a.description, a.capacity, a.seats_taken, p.name, p.country_code,
       ST_Distance(a.location, q.origin) AS distance_m
  FROM adventures a
  JOIN places p ON p.id = a.place_id
 CROSS JOIN (SELECT ST_SetSRID(ST_MakePoint(:lng, :lat), 4326)::geography AS origin) q
 WHERE a.status = 'OPEN'
   AND a.organizer_id <> :viewerId
   AND ST_DWithin(a.location, q.origin, :radiusMeters)
   AND a.trip_dates && daterange(:from, :to, '[]')
   AND (:noStyles OR a.styles && CAST(:styles AS text[]))
   AND (a.start_date, a.id) > (:cursorDate, :cursorId)
 ORDER BY a.start_date, a.id
 LIMIT :limitPlusOne;
```

- [ ] Keyset pagination: the cursor is the base64url encoding of the last row's `start_date` and `id`. Fetch one extra row to know whether a next page exists. No `OFFSET`. Leave the cursor predicate out of the query for the first page.
- [ ] Select columns by name. `location` and `trip_dates` are for filtering, not for mapping into Java.
- [ ] Response shape: `items` and `nextCursor`.

### Matches

`GET /adventures/{id}/matches`, organizer only: other open adventures near mine with overlapping dates, ranked by a score. Start with these weights and adjust later.

| Component | Weight | Definition |
|---|---|---|
| Date overlap | 0.5 | Days in common divided by the length of my trip |
| Style similarity | 0.3 | Shared styles divided by all styles across both trips |
| Proximity | 0.2 | One minus distance divided by the search radius |

### Index study

- [ ] A seed script using `generate_series` that inserts 100,000 adventures at random places, with random dates over the next 180 days and one to three random styles.
- [ ] Run the search with `EXPLAIN (ANALYZE, BUFFERS)` with and without the GiST and GIN indexes. Record both plans and timings in `docs/perf/phase-1-baseline.md`. This is the first measured before-and-after.

### Tests

- [ ] Integration: a trip inside the radius is returned and one just outside is not; date ranges that only touch on one day count as overlapping; the style filter matches any shared style; paging through results while new rows are inserted yields no duplicates and no gaps; the caller's own trips are excluded.

**Done when:** the tests pass and the index study is written up.

**Be able to explain:** why `geography` and not `geometry`; what a GiST index does for range overlap; keyset versus offset pagination; when you would add a search engine.

## M5: Adventure (join requests and seat reservation)

**Goal:** the core invariant. A trip never has more accepted travellers than seats, whatever the concurrency.

### Schema (`V5__join_requests.sql`)

```sql
CREATE TABLE join_requests (
  id           uuid PRIMARY KEY,
  adventure_id uuid NOT NULL REFERENCES adventures (id),
  requester_id uuid NOT NULL,
  message      text CHECK (char_length(message) <= 300),
  status       text NOT NULL DEFAULT 'PENDING'
               CHECK (status IN ('PENDING', 'ACCEPTED', 'REJECTED', 'WITHDRAWN', 'EXPIRED')),
  expires_at   timestamptz NOT NULL,
  decided_at   timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX join_requests_one_active_idx
  ON join_requests (adventure_id, requester_id) WHERE status IN ('PENDING', 'ACCEPTED');
CREATE INDEX join_requests_adventure_idx ON join_requests (adventure_id, status, created_at);
CREATE INDEX join_requests_requester_idx ON join_requests (requester_id, created_at DESC);
CREATE INDEX join_requests_expiry_idx    ON join_requests (expires_at) WHERE status = 'PENDING';

CREATE TABLE adventure_members (
  adventure_id uuid NOT NULL REFERENCES adventures (id),
  user_id      uuid NOT NULL,
  role         text NOT NULL CHECK (role IN ('ORGANIZER', 'MEMBER')),
  joined_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (adventure_id, user_id)
);
CREATE INDEX adventure_members_user_idx ON adventure_members (user_id);
```

The organizer is inserted as a member with role `ORGANIZER` when the adventure is created and does not use a seat.

### State machine

| From | Action | Who | To | Side effects |
|---|---|---|---|---|
| none | create | Verified traveller who is not the organizer | `PENDING` | `expires_at` set to 72 hours ahead |
| `PENDING` | accept | Organizer | `ACCEPTED` | Take a seat, add the member, add them to the conversation |
| `PENDING` | reject | Organizer | `REJECTED` | |
| `PENDING` | withdraw | Requester | `WITHDRAWN` | |
| `PENDING` | expire | System (Phase 2) | `EXPIRED` | |
| `ACCEPTED` | accept again | Organizer | `ACCEPTED` | None; returns 200 |
| any other pair | | | | 409 `INVALID_STATE_TRANSITION` |

### Accept

Start with plain reads: 404 if the request does not exist, 403 if the caller is not the organizer, and 200 straight away if the request is already `ACCEPTED`. Then, in one transaction:

```sql
-- 1. Take a seat, only if one remains. This also locks the adventure row.
UPDATE adventures
   SET seats_taken = seats_taken + 1,
       status      = CASE WHEN seats_taken + 1 >= capacity THEN 'FULL' ELSE status END,
       updated_at  = now()
 WHERE id = :adventureId AND status = 'OPEN' AND seats_taken < capacity;
-- 0 rows: nothing was written. 409 ADVENTURE_FULL or ADVENTURE_NOT_OPEN.

-- 2. Move the request, only if it is still pending
UPDATE join_requests
   SET status = 'ACCEPTED', decided_at = now()
 WHERE id = :requestId AND status = 'PENDING' AND expires_at > now();
-- 0 rows: throw, which rolls back the seat from step 1. Then re-read the request:
-- ACCEPTED (another call won the race) returns 200; anything else is 409.

-- 3. Record the membership
INSERT INTO adventure_members (adventure_id, user_id, role) VALUES (:adventureId, :requesterId, 'MEMBER');
```

- [ ] Lock order: every transaction that touches both tables locks the adventure row first, then request rows. Accept and cancel both follow it, so they cannot deadlock each other.
- [ ] Creating a request reads the adventure with `SELECT ... FOR SHARE`. A concurrent cancel then waits for the insert to commit and rejects it with the other pending requests, so no pending request is left behind on a cancelled trip.
- [ ] Repository update methods are `@Modifying(clearAutomatically = true, flushAutomatically = true)`.
- [ ] After the transaction commits, tell chat. Hide this behind an interface, `MembershipNotifier`. The Phase 1 implementation makes an HTTP call; Phase 2 replaces it with an outbox event without touching the service logic.
- [ ] If the chat call fails, return 502 `CHAT_UNAVAILABLE`. The seat is already taken; a retry of accept is idempotent and calls chat again. This weakness is deliberate and is what Phase 2 removes.
- [ ] The remote call is never made inside the database transaction.

### Endpoints

| Method and path | Rules |
|---|---|
| `POST /adventures/{id}/join-requests` | Verified, not the organizer, adventure `OPEN`. `Idempotency-Key` required. Body: optional `message`. Errors: 409 `REQUEST_ALREADY_EXISTS`, 409 `ADVENTURE_NOT_OPEN`, 422 `CANNOT_JOIN_OWN_ADVENTURE` |
| `GET /join-requests?direction=&status=` | `incoming` lists requests on trips I organize; `outgoing` lists mine. This feeds the app's Requests tab |
| `GET /adventures/{id}/join-requests` | Organizer only |
| `POST /join-requests/{id}/accept` | Organizer only; idempotent |
| `POST /join-requests/{id}/reject` | Organizer only; idempotent |

### Tests

- [ ] Unit: one parameterised test covering every state and action pair in the table.
- [ ] Integration, seat safety: an adventure with 5 seats and 50 pending requests; 50 threads released together by a latch each accept a different request. Assert exactly 5 responses are 200, 45 are 409, `seats_taken` is 5, there are 5 members plus the organizer, and status is `FULL`.
- [ ] Integration, double accept: two threads accept the same request; one seat is taken and both get 200.
- [ ] Integration, cancel against accept: run a cancel and an accept on the same trip at the same moment, 100 times. No call fails with a deadlock or a 500, and the end state is always consistent: either the member was accepted before the cancel, or the request was rejected by it.
- [ ] Integration: a second active request from the same traveller returns 409; a request on a full trip returns 409; withdraw and reject work once and are then idempotent.

**Done when:** the seat-safety test passes repeatedly (run it 20 times in a loop).

**Be able to explain:** why a conditional update and not a distributed lock; what `READ COMMITTED` does when two updates hit the same row; the role of the check constraint; why lock ordering matters; why the chat call sits outside the transaction.

## M6: Chat (conversations and messages)

**Goal:** message history per trip, stored in MongoDB, readable only by members. REST only in this phase.

### Collections

| Collection | Fields | Indexes |
|---|---|---|
| `conversations` | `adventureId`, `memberIds[]`, `lastMessage` (id, sender, preview, time), `lastMessageAt`, `createdAt` | Unique on `adventureId`; `{memberIds: 1, lastMessageAt: -1}` |
| `messages` | `conversationId`, `senderId`, `clientMessageId`, `type` (`TEXT` or `SYSTEM`), `body` (2,000 characters maximum), `createdAt` | `{conversationId: 1, _id: -1}`; unique on `{conversationId, senderId, clientMessageId}` |
| `read_states` | `conversationId`, `userId`, `lastReadMessageId` | Unique on `{conversationId, userId}` |

- [ ] One conversation per adventure. A two-person trip is simply a conversation with two members.
- [ ] User IDs are stored as strings, which avoids the binary UUID representation settings.
- [ ] Indexes are declared on the document classes with automatic index creation switched on. Say in the README that production would create them through migrations.

### Endpoints

| Method and path | Rules |
|---|---|
| `GET /conversations` | The caller's conversations, most recent first, each with an unread count capped at 99 |
| `GET /conversations/{id}/messages?before=&limit=` | Members only (403 otherwise). Newest first; `before` is a message ID |
| `POST /conversations/{id}/messages` | Body: `clientMessageId`, `body`. A repeated `clientMessageId` returns the existing message with 200 instead of 201 |
| `PUT /conversations/{id}/read` | Body: `lastReadMessageId`. Only ever moves forward |
| `PUT /internal/conversations/{adventureId}/members` | Body: `memberIds`. Creates the conversation if missing and adds the members with `$addToSet`. Protected by a shared secret header. Temporary; deleted in Phase 2 |

- [ ] Sending writes the message first, then updates the conversation's preview. There is no multi-document transaction; a stale preview repairs itself on the next message.
- [ ] `ObjectId` values sort by creation time, so the message ID is the pagination cursor.

### Wire adventure to chat

- [ ] Implement `HttpMembershipNotifier` in adventure with `RestClient`, a two-second timeout and the shared secret header. On first accept it sends both the organizer and the new member.

### Tests

- [ ] Integration (Testcontainers MongoDB): paging through history returns each message once; a duplicate `clientMessageId` stores one document; a non-member gets 403; the read marker never moves backward; unread counts are correct for two members.

**Done when:** after an accept, both organizer and traveller can list the conversation and exchange messages through the REST API.

**Be able to explain:** why messages suit a document store; how the client-generated ID makes sending idempotent; why you avoided a multi-document transaction.

## Things that will trip you up

- **Jackson 3:** Boot 4 uses Jackson 3, whose databind classes live under `tools.jackson`. Most tutorials written before 2026 import `com.fasterxml.jackson.databind.ObjectMapper`.
- **Test annotations:** `@MockitoBean` replaces the older `@MockBean`.
- **Schema validation:** with `ddl-auto=validate`, column types such as `char(2)` or `citext` fail the start-up check against a `String` field. Use `text`.
- **Native updates:** they bypass Hibernate's first-level cache. Without `clearAutomatically`, a later read in the same transaction returns stale data.
- **Generated columns:** if your PostGIS build rejects the `location` expression as not immutable, drop the generated column and set `location` explicitly in the insert statement.
- **Emulation:** do not fall back to the amd64 `postgis/postgis` image under emulation; it is slow and makes the concurrency tests flaky.
- **Connection pool:** Hikari defaults to 10 connections, so the 50-thread test queues for connections. That is fine; do not raise the pool to make the test faster.
- **First test run:** Testcontainers pulls images on first use, so the first `./mvnw verify` is slow.
