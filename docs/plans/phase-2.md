# Phase 2 implementation plan: messaging, Redis and distributed patterns

Parent document: [../ARCHITECTURE.md](../ARCHITECTURE.md). Previous: [phase-1.md](phase-1.md).

**Status (2026-11-11):** not started. Nothing here has been compiled or run yet; the SQL and Compose snippets are untested drafts. Versions were checked on 2026-11-10 against Spring Initializr, Maven Central and Docker Hub.

## Outcome

- Accepting a join request no longer depends on chat being up. Services exchange events through Kafka, published from a transactional outbox.
- Chat delivers messages in real time across more than one instance.
- A notification service turns events into an in-app inbox and push messages, with retries and a dead-letter store.
- All traffic enters through a gateway that validates tokens and rate-limits callers.
- Every request can be traced from HTTP through Kafka to its consumers.
- A second load test, on the same machine as the Phase 1 baseline, shows what changed.

## Fixed decisions

| Decision | Choice | Reason |
|---|---|---|
| Broker | `apache/kafka:4.4.0`, one node in KRaft mode, three partitions per topic | Same client and semantics as a real cluster, small enough for a laptop |
| Message format | A JSON envelope sent as a string; payload records in a shared `libs/events` module | One repo gives compile-time contracts; no schema registry needed |
| Publishing | Transactional outbox with a polling relay; one active relay per service | Removes the dual write, and a single relay keeps per-adventure order |
| Consumer retries | Retry in place for order-sensitive consumers; retry topics for notifications | A poison message must not reorder membership events, but may be set aside for a push |
| Deduplication | Natural idempotency where possible; a `processed_events` table otherwise | Kafka delivers at least once |
| Redis | `redis:7-alpine` | Gateway rate limits, chat fan-out, presence, caches |
| Gateway | Spring Cloud Gateway on WebFlux, routes defined in Java | It has the Redis rate limiter and proxies WebSockets |
| Scheduler locks | ShedLock 7.x with the JDBC provider | The lock lives in the same database as the data it protects |
| Observability | OTLP export to one `grafana/otel-lgtm` container | Metrics, traces and logs in one place with no per-tool setup |
| Push delivery | A `PushSender` interface; a logging implementation now, FCM in Phase 3 | The retry and dead-letter path can be built and tested without a phone |
| Fault injection | Toxiproxy between services, plus `docker compose stop` | Latency and outages on demand, with no test code in production paths |

## Event contracts

### Envelope

```json
{
  "eventId": "0b7c0d3e-...",
  "type": "JoinRequestAccepted",
  "version": 1,
  "aggregateId": "f3a1...",
  "occurredAt": "2026-11-10T10:15:30Z",
  "payload": { }
}
```

- The Kafka record key is `aggregateId`, so all events for one adventure land on one partition, in order.
- Kafka headers carry `event-id`, `event-type` and `traceparent`.
- Consumers ignore event types and fields they do not know. Changes to a payload are additive; a breaking change gets a new `version`.

### Catalogue

| Event | Topic | Payload beyond the envelope | Consumers |
|---|---|---|---|
| `AdventureCreated` | `adventure.events` | `organizerId`, `placeId`, `placeName`, `lat`, `lng`, `startDate`, `endDate`, `styles`, `description`, `capacity` | Planner (Phase 3) |
| `AdventureUpdated` | `adventure.events` | The same fields, plus the entity `version` | Planner (Phase 3) |
| `AdventureCancelled` | `adventure.events` | `organizerId`, `placeName`, `memberIds`, `pendingRequesterIds` | Chat, notification |
| `JoinRequestCreated` | `adventure.events` | `requestId`, `organizerId`, `requesterId`, `placeName` | Notification |
| `JoinRequestAccepted` | `adventure.events` | `requestId`, `organizerId`, `requesterId`, `placeName`, `seatsTaken`, `capacity` | Chat, notification |
| `JoinRequestRejected` | `adventure.events` | `requestId`, `requesterId`, `placeName` | Notification |
| `JoinRequestWithdrawn` | `adventure.events` | `requestId`, `organizerId`, `requesterId` | None yet |
| `JoinRequestExpired` | `adventure.events` | `requestId`, `requesterId`, `placeName` | Notification |
| `UserRegistered` | `user.events` | `displayName` | Adventure, notification |
| `ProfileUpdated` | `user.events` | `displayName` | Notification |
| `UserVerified` | `user.events` | | Adventure, notification |
| `UserSuspended` | `user.events` | | Adventure |
| `MessageSent` | `chat.events` | `messageId`, `senderId`, `preview`, `offlineRecipientIds` | Notification |

Events carry the data consumers need (place name, affected user IDs), so no consumer has to call back to the producer.

## M2: Outbox and relay in adventure

**Goal:** every state change in adventure produces an event that cannot be lost and cannot be published without the change.

### Schema

```sql
-- adventure: V6__outbox.sql
CREATE TABLE outbox (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id     uuid  NOT NULL UNIQUE,
  topic        text  NOT NULL,
  msg_key      text  NOT NULL,
  event_type   text  NOT NULL,
  payload      jsonb NOT NULL,              -- the full envelope
  headers      jsonb NOT NULL DEFAULT '{}', -- traceparent captured at write time
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz
);
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;
```

### Writing events

- [ ] An `OutboxWriter` that inserts one row. It must be called inside the caller's transaction and must fail if there is none (`Propagation.MANDATORY`).
- [ ] Emit an event from every write path: create, update and cancel an adventure; create, accept, reject and withdraw a request.
- [ ] Rule: change the aggregate first (and flush, if the change went through JPA), then insert the outbox row. The second transaction on the same adventure then waits on the row lock before it gets its outbox ID, so IDs follow the order in which related changes happened.
- [ ] Replace `HttpMembershipNotifier` with `OutboxMembershipNotifier`. The accept logic itself does not change.

### Relay

Every 200 ms, in one transaction:

1. `SELECT pg_try_advisory_xact_lock(:relayLockId)`. If it returns false, another instance is relaying; stop.
2. Select up to 200 unpublished rows ordered by `id`.
3. Send each to Kafka in that order and wait for every acknowledgement, with a bounded timeout.
4. Mark those rows published. Commit, which also releases the lock.

If any send fails, the transaction rolls back and the batch is retried on the next tick. Some of it may already have reached Kafka, so duplicates are possible and consumers must tolerate them.

Why one active relay and not several working in parallel with `SKIP LOCKED`: two relays publishing different batches at the same time can emit a later event for an adventure before an earlier one. `SKIP LOCKED` is right for jobs whose order does not matter, and it is used that way in M8. For an ordered event stream, one publisher at a time is the simple correct answer, and a batch of 200 every 200 ms is far more throughput than this system needs.

- [ ] Producer settings: `acks=all`, idempotence on (both are defaults; state them anyway), delivery timeout of 10 seconds so the relay transaction cannot hang.
- [ ] Optional: wake the relay immediately after commit with a `@TransactionalEventListener`, keeping the timer as the fallback. This cuts publish latency without tighter polling.
- [ ] A gauge for the number of unpublished rows. It is the first thing to look at when Kafka is down.

### Tests

- [ ] Integration: an accept writes exactly one outbox row; a failed accept (trip full) writes none.
- [ ] Integration: the relay publishes rows in `id` order and marks them.
- [ ] Integration: simulate a crash between send and mark (make the mark step throw once). The rows are published again on the next tick, with the same `eventId`.
- [ ] Integration: with Kafka stopped, accept still returns 200 and rows accumulate; when Kafka returns, they drain in order.
- [ ] Integration: two relay beans against one database never publish concurrently.

**Done when:** every adventure write path emits its event and all five tests pass.

**Be able to explain:** the dual-write problem; why the outbox gives at-least-once delivery and not exactly-once; why a single relay preserves order and what you would do at higher volume (partition the outbox by key, or change data capture with Debezium).

## M3: Chat consumes events; remove the synchronous call

**Goal:** chat learns about membership from Kafka. Adventure no longer knows chat exists.

- [ ] A listener on `adventure.events` in consumer group `chat.adventure-events`, starting from the earliest offset.
- [ ] `JoinRequestAccepted`: create the conversation if missing and add the organizer and requester with `$addToSet`. This is idempotent by nature, so no deduplication table is needed.
- [ ] `AdventureCancelled`: mark the conversation archived. Archived conversations are readable but reject new messages.
- [ ] Error handling: retry in place with back-off, about five attempts over half a minute, then send the record to a dead-letter topic and raise a metric. This consumer depends on order, so it must not use retry topics.
- [ ] Delete the internal endpoint in chat, the shared secret, and the REST client and `spring-boot-starter-restclient` dependency in adventure.

### Tests

- [ ] Integration (Kafka and MongoDB): one accepted event adds both members; the same event delivered twice leaves the conversation unchanged; an unknown event type is skipped without error.
- [ ] End to end: with chat stopped, accept returns 200. After chat starts, the member appears.

**Done when:** the Phase 1 smoke script passes with no HTTP call between adventure and chat.

**Be able to explain:** eventual consistency in this flow and what the user sees during the gap; why `$addToSet` makes deduplication unnecessary; why order-sensitive consumers retry in place.

## M4: Notification service

**Goal:** events become an inbox entry and a push attempt, exactly once in the inbox, with failures set aside and replayable.

### Collections

| Collection | Fields | Indexes |
|---|---|---|
| `notifications` | `userId`, `eventId`, `type`, `title`, `body`, `data` (adventure, request or conversation IDs), `pushStatus` (`PENDING`, `SENT`, `SKIPPED`), `readAt`, `createdAt` | Unique on `{eventId, userId}`; `{userId: 1, _id: -1}`; TTL of 90 days on `createdAt` |
| `devices` | `_id` (the push token), `userId`, `platform`, `updatedAt` | `{userId: 1}` |
| `user_names` | `_id` (user ID), `displayName` | Fed from `user.events`, so messages can name people without calling identity |
| `dead_letters` | `eventId`, `topic`, `key`, `payload`, `error`, `failedAt`, `replayedAt` | `{failedAt: -1}` |

### Who is told what

| Event | Recipient | Message |
|---|---|---|
| `JoinRequestCreated` | Organizer | "Asha wants to join your Goa trip" |
| `JoinRequestAccepted` | Requester | "You're in: Goa" |
| `JoinRequestRejected` | Requester | "Your request for Goa was declined" |
| `JoinRequestExpired` | Requester | "Your request for Goa expired" |
| `AdventureCancelled` | Members and pending requesters | "The Goa trip was cancelled" |
| `UserVerified` | The user | "Your profile is verified" |
| `MessageSent` | Offline members of the conversation | Sender name and message preview |

### Processing

1. Insert the inbox document. A duplicate-key error means this event was already handled for this user; carry on to step 2 only if its `pushStatus` is still `PENDING`.
2. Send the push through `PushSender`, wrapped in a circuit breaker and a two-second timeout.
3. On success set `pushStatus` to `SENT`. On failure throw, so the record goes to the next retry topic.

The inbox is exactly-once because of the unique index. Push is at-least-once; give each push a collapse key equal to the event ID so a device shows a duplicate only once.

- [ ] Non-blocking retries with Spring Kafka's retry-topic support: four attempts with exponential back-off (about 1, 5 and 25 seconds), then the dead-letter topic. Use topic suffixes that include `notification`, so another consumer group can add its own retry topics later.
- [ ] A dead-letter handler that stores the failed record in `dead_letters`.
- [ ] `PushSender` implementations: `LoggingPushSender` as the default, and a test double that fails a set number of times.
- [ ] Circuit breaker named `push`: opens at 50% failures over the last 20 calls, stays open 30 seconds, then allows 3 trial calls.

### Endpoints

| Method and path | Auth | Notes |
|---|---|---|
| `GET /notifications?cursor=&limit=` | user | Newest first |
| `GET /notifications/unread-count` | user | |
| `PUT /notifications/{id}/read` | user | |
| `PUT /devices/{token}` | user | Body: `platform`. Registers or re-assigns a push token |
| `DELETE /devices/{token}` | user | On logout |
| `GET /admin/dead-letters` | admin | |
| `POST /admin/dead-letters/{id}/replay` | admin | Republishes the stored payload to its original topic with the same `eventId` |

### Tests

- [ ] Integration: the same event twice produces one inbox document and one push.
- [ ] Integration: the sender fails twice and then succeeds; one document, `pushStatus` is `SENT`.
- [ ] Integration: the sender always fails; the record ends in `dead_letters`; after the sender is fixed, replay delivers it.
- [ ] Integration: after enough failures the breaker opens and calls stop reaching the sender; it closes again after the wait.
- [ ] End to end: with notification stopped, accept returns 200; on restart the backlog drains and nothing is duplicated.

**Done when:** the full flow produces the expected inbox entries for both users, and the dead-letter replay works from the API.

**Be able to explain:** blocking versus non-blocking retries and when each is wrong; what a dead-letter topic is for; the three circuit breaker states; why the inbox and the push have different delivery guarantees.

## M5: Identity events and user snapshots

**Goal:** verification and suspension take effect in other services within seconds, without anyone calling identity.

### Identity

- [ ] Add the same `outbox` table, writer and relay. Move the shared pieces into `libs/common` now that two services use them.
- [ ] Emit `UserRegistered`, `ProfileUpdated` (when the display name changes), `UserVerified` and `UserSuspended` to `user.events`, keyed by user ID.
- [ ] `POST /admin/users/{id}/suspend`: sets the status, revokes every refresh token for the user and emits the event.

### Adventure

```sql
-- adventure: V7__user_snapshots.sql
CREATE TABLE user_snapshots (
  user_id       uuid PRIMARY KEY,
  verified      boolean NOT NULL DEFAULT false,
  status        text    NOT NULL DEFAULT 'ACTIVE',
  last_event_at timestamptz NOT NULL
);

CREATE TABLE processed_events (
  consumer     text NOT NULL,
  event_id     uuid NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, event_id)
);
```

- [ ] A listener on `user.events` in group `adventure.user-events`. In one transaction, insert into `processed_events` with `ON CONFLICT DO NOTHING`; if no row was inserted, skip; otherwise upsert the snapshot.
- [ ] The upsert only applies when the event is newer than `last_event_at`, so a late duplicate cannot overwrite newer state.
- [ ] Enforcement when creating a trip or a request: the caller must be verified by token claim or by snapshot, and must not be suspended in the snapshot. A missing snapshot falls back to the claim.

### Tests

- [ ] Integration: a user verified after login can create a trip without logging in again, once the event has arrived.
- [ ] Integration: a suspended user holding a valid access token is refused within seconds.
- [ ] Integration: `UserSuspended` followed by a delayed duplicate of an older `UserVerified` leaves the user suspended.

**Done when:** suspension is enforced in adventure before the user's access token expires.

**Be able to explain:** event-carried state transfer; why JWT claims alone cannot revoke access quickly; how the timestamp guard handles out-of-order delivery.

## M6: Gateway

**Goal:** one public entry point. Services stop being reachable directly.

### Routes

| Path | Target |
|---|---|
| `/auth/**`, `/users/**`, `/.well-known/**`, `/admin/verifications/**`, `/admin/users/**` | identity |
| `/adventures/**`, `/join-requests/**`, `/places/**` | adventure |
| `/conversations/**`, `/ws/**` (WebSocket) | chat |
| `/notifications/**`, `/devices/**`, `/admin/dead-letters/**` | notification |

- [ ] Define routes in Java with `RouteLocatorBuilder`.
- [ ] Security: the gateway validates the JWT against identity's JWKS and forwards the `Authorization` header unchanged. Services keep validating it themselves. Public paths are `/auth/**` and `/.well-known/**`.
- [ ] Remove the published ports of the four services from Compose; only the gateway (8080) is exposed.
- [ ] CORS configuration, ready for the admin console in Phase 3.

### Rate limits

Token buckets in Redis through the gateway's `RedisRateLimiter`. The key is the user ID for authenticated calls and the client IP otherwise.

| Scope | Limit | Bucket settings |
|---|---|---|
| `/auth/login`, `/auth/register`, per IP | 5 per minute | Refill 1 token per second, capacity 60, each request costs 12 |
| Everything else, per user | 20 per second, bursts to 40 | Refill 20, capacity 40, cost 1 |

- [ ] A rejected call returns 429 with the limiter's remaining-tokens headers. The default response has no body; add one only if a client needs it.
- [ ] The limiter allows traffic when Redis is unreachable. That is a deliberate choice of availability over protection; write it down in the README.

### Resilience

- [ ] A response timeout per route (2 seconds; 5 for search).
- [ ] A circuit breaker per downstream service with a fallback that returns 503 as problem JSON.
- [ ] Retries only for `GET`, at most twice, with back-off.

### Tests

- [ ] Integration (Redis container, stubbed downstream): a burst beyond the bucket gets 429; two users have independent buckets; with Redis stopped, requests pass.
- [ ] Integration: a missing or invalid token is rejected at the gateway and never reaches the downstream stub.
- [ ] Integration: when the downstream stub hangs, the caller gets 503 within the timeout.

**Done when:** the smoke script passes using only port 8080.

**Be able to explain:** the token bucket algorithm and why the check must be atomic; fail-open versus fail-closed; why services still validate tokens behind the gateway; why retries are limited to idempotent calls.

## M7: Real-time chat

**Goal:** a message reaches every connected member within a second, whichever chat instance they are connected to.

- [ ] A STOMP endpoint at `/ws` with the simple in-memory broker for `/topic`.
- [ ] Authentication on the STOMP `CONNECT` frame: a channel interceptor reads the `Authorization` header, validates the JWT and sets the user on the session.
- [ ] Authorization on `SUBSCRIBE`: only members may subscribe to `/topic/conversations/{id}`.
- [ ] Sending stays on REST (`POST /conversations/{id}/messages`), so there is one write path with normal HTTP status codes and retry behaviour. The socket is for delivery.
- [ ] Fan-out: after saving a message, publish it to the Redis channel `chat:conv:{id}`. Every instance subscribes to the pattern and forwards to its own local subscribers.
- [ ] Typing indicators: `SEND /app/conversations/{id}/typing`, relayed through the same Redis channel and never stored.
- [ ] Presence: on connect set `presence:{userId}` with a 60-second expiry and refresh it while the session lives; delete it on disconnect.
- [ ] After saving a message, publish `MessageSent` to `chat.events` with the members who have no presence key. Notification pushes to them.

Two things to state plainly in the README:

- Redis pub/sub does not store messages. A client that was disconnected fetches what it missed over REST, using the last message ID it has.
- `MessageSent` is published after the MongoDB write, without an outbox. If that publish fails, a push is lost but the message is not. Change streams would close the gap if it ever mattered.

### Tests

- [ ] Integration: a subscriber receives a message sent by another member; a non-member's subscription is refused; a connection without a valid token is refused.
- [ ] Integration, the important one: start two chat application contexts on different ports sharing one Redis and one MongoDB. A message posted to the first is received by a subscriber connected to the second.
- [ ] Integration: a member with no presence key appears in `offlineRecipientIds`; a connected member does not.

**Done when:** two clients on different instances see each other's messages live, and an offline member gets an inbox entry.

**Be able to explain:** why the in-memory broker alone breaks with two instances; why Redis pub/sub is acceptable here despite losing messages; how a reconnecting client catches up; why sending uses REST.

## M8: Caching, quota and scheduled jobs

**Goal:** the read path is cheaper, and housekeeping runs exactly once however many instances exist.

### Caching in adventure

| Cache | Key | TTL | Invalidation |
|---|---|---|---|
| Adventure details | Adventure ID | 5 minutes | Evicted after commit on update, cancel and seat change |
| Search, first page only | Geohash cell (precision 5), radius bucket, `from`, `to`, sorted styles | 60 seconds | None; new trips appear within a minute |

- [ ] Quantise before querying: snap the origin to the centre of its geohash cell and round the radius up to a bucket (25, 50, 100, 250 or 500 km), then run the query on those values. The key must describe exactly the question that was asked, or the cache returns the answer to a different one.
- [ ] Use Spring's cache abstraction over Redis with statistics on, so hit and miss counts are exported as metrics.
- [ ] Cache only data that is the same for every viewer. `viewerRequest` is fetched separately on each call.
- [ ] Evict after the transaction commits, not inside it.
- [ ] Writes never read from the cache. Seat checks always go to the database.

### Quota

- [ ] At most 20 join requests per user per day, checked with a count on `join_requests` using the existing `(requester_id, created_at)` index. Exceeding it returns 429 `JOIN_REQUEST_QUOTA_EXCEEDED`. This is a plain query on purpose: the data is already in Postgres and the rate is low, so a Redis counter would add a second source of truth for nothing.

### Scheduled jobs (ShedLock, JDBC provider)

| Job | Schedule | Work |
|---|---|---|
| Expire requests | Every 5 minutes | Batches of 500: select pending rows past `expires_at` with `FOR UPDATE SKIP LOCKED`, set `EXPIRED`, write one `JoinRequestExpired` per row to the outbox |
| Complete adventures | Daily | `OPEN` or `FULL` trips whose `end_date` has passed become `COMPLETED` |
| Purge | Daily | Delete idempotency keys older than 48 hours and published outbox rows older than 7 days |

- [ ] Add the `shedlock` table through Flyway.
- [ ] Set `lockAtMostFor` above the worst-case run time and `lockAtLeastFor` to a few seconds.

The relay from M2 uses an advisory lock, not ShedLock. ShedLock suits jobs that run every few minutes; a 200 ms poller needs a lock that costs one cheap statement and disappears with its transaction.

### Tests

- [ ] Integration: a second read of the same adventure does not query the database; an update evicts it.
- [ ] Integration: the 21st request in a day returns 429.
- [ ] Integration: expired requests become `EXPIRED` and emit events; requests not yet due are untouched.
- [ ] Integration: with two scheduler instances, each run of the expiry job executes once.

**Done when:** cache hit ratio is visible as a metric and the expiry job works with two adventure instances running.

**Be able to explain:** cache-aside and its stale-read race; why search uses a short TTL instead of invalidation; why `SKIP LOCKED` is right for the expiry job and wrong for the relay; what happens if a job outlives `lockAtMostFor`.

## M9: Observability

**Goal:** one trace shows a join request from the gateway to the push attempt, and one dashboard shows the health of the system.

- [ ] Add `spring-boot-starter-opentelemetry` to every service and export over OTLP to the `otel-lgtm` container.
- [ ] Turn on observation for the Kafka template and listener containers, so trace context travels in record headers.
- [ ] Bridge the outbox: capture the current `traceparent` into `outbox.headers` when the row is written, and set it as a Kafka header in the relay. Without this the trace ends at the database commit.
- [ ] Structured JSON logs that include the trace ID.
- [ ] One Grafana dashboard, exported to `infra/grafana/`:

| Panel | Source |
|---|---|
| Request rate, error rate and latency per route | HTTP server metrics |
| Consumer lag per group | Kafka client metrics |
| Outbox backlog | The gauge from M2 |
| Cache hit ratio | Cache metrics from M8 |
| Rate-limited requests | Gateway metrics |

## Things that will trip you up

- **Kafka listeners in Compose:** a container must use `kafka:9092` and the host `localhost:29092`. Mixing them up gives a client that connects and then hangs.
- **Offset reset:** a new consumer group starts at the latest offset by default and silently misses earlier events. Projections should start from the earliest.
- **Retry annotations:** take the retry-topic attribute names from the Spring Kafka 4 reference. Older tutorials use spring-retry types that Boot 4 no longer manages.
- **Serialisation:** send the envelope as a string. Spring's JSON serialiser adds type headers that couple consumers to the producer's class names.
- **Listener transactions:** commit the database work before the offset is committed. The reverse order loses events on a crash.
- **Reactive gateway:** never make a blocking call inside a gateway filter.
- **Rate limiter:** it needs the reactive Redis starter, not the blocking one.
- **Scheduling:** without ShedLock every instance runs every job.
- **Cache contents:** anything viewer-specific in a shared cache is a data leak.
- **Scaling chat locally:** `docker compose up --scale chat=2` works only once chat has no published host port, which is the case after M6.
